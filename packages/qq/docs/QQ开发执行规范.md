# QQ 开发执行规范

本文是 QQ 子项目的开发规则。`packages/qq/AGENTS.md` 是自动读取的硬规则入口，本文说明完整流程和检查方法。

## Summary

开发必须限定在用户确认的范围内，按模块完成实现、文档、日志和验证。代码保持完整，注释保持少量且易懂，用户看到的名称和文案使用普通中文。

## 规则优先级

仓库根规则、`packages/AGENTS.md` 和 `packages/qq/AGENTS.md` 优先于本文。

用户明确指定的本次范围优先于旧计划和参考项目。参考项目只作为行为来源，不能直接复制它的宿主结构、阻塞机制、数据库或页面。

项目现有测试、类型和公开接口契约优先于个人偏好。若与本文冲突，先遵守项目规则，再在开发日志记录原因。

## 开发前阅读

开始修改前至少阅读：

1. [根目录规则](../../../AGENTS.md)。
2. [包目录规则](../../AGENTS.md)。
3. [QQ 子项目规则](../AGENTS.md)。
4. [QQ 开发日志](QQ开发日志.md)。
5. 目标包的 `README.md`、源码入口和相关测试。
6. 涉及回复、队列、媒体、记忆或持久化时，再阅读对应的 `dev-spec.md`、`mechanism-map.md` 或专题规范。

先确认现有行为，再确定改动。不能只根据文件名判断模块已经接入。

## 模块开发流程

每个模块按下面顺序执行：

1. 在开发日志新增一条任务，写明用户要求、影响范围、不做什么和验收项。
2. 读源码、测试和文档，确认当前行为与缺口。
3. 只修改本任务需要的模块，不顺带做无关重构。
4. 实现完整主链，包括入口、配置、失败处理、清理和文档。
5. 补行为测试；涉及共享接口时补类型检查和集成测试。
6. 运行针对性 lint、类型检查和测试。
7. 同步 README、状态表和相关规范。
8. 在开发日志填写改动文件、验证结果和剩余问题。
9. 所有验收项完成后打勾；未验证或半成品不能标记完成。

## 开发日志

开发日志是任务进度的唯一记录位置，文件是[QQ 开发日志](QQ开发日志.md)。

每个任务至少包含：

- 日期。
- 用户范围。
- 状态。
- 模块和文件。
- 已做改动。
- 验证命令与结果。
- 未完成项。

模块完成前必须更新日志。没有日志记录的任务不能直接宣布完成。

## 注释规则

内部注释只在代码意图不明显时使用，原则如下：

| 要求 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 数量 | 一个模块少量必要注释 | 每行、每个分支都写注释 |
| 长度 | 一行短句 | 多段长篇解释 |
| 语言 | 普通中文 | 复杂术语、内部黑话、夸张说法 |
| 内容 | 说明为什么这样做 | 重复代码表面行为 |
| 格式 | 纯文字 | 装饰线、表情符号、口号 |

公开 API 继续遵守仓库要求的契约文档，但内容要直接、简短，不写实现过程。

注释里不使用“频道、账本、债务、遗书、死亡威胁、能力面、接缝、宿主”等难懂或容易误导的说法。必须描述已有公开类型或协议字段时，标识保持原样，解释使用普通中文。

## 命名与文案

新增代码、提示词、配置说明和用户文案优先使用日常词：

| 不使用 | 改用 |
| --- | --- |
| 频道 | 群聊、私聊或连接 |
| 账本、记账 | 记录、用量记录、状态记录 |
| 债务 | 还没完成的事、欠着的事 |
| 遗书 | 重要留言，或按具体场景描述 |
| 死亡威胁、死亡倒计时 | 不使用；改成普通情绪或休息状态 |
| 宿主接缝、能力面 | 服务接口、连接位置 |
| 投递器、投递成功 | 发送、已经发出 |
| 载体、事件载荷 | 消息内容、数据 |

角色名字使用正常的人名或用户配置的名称。除非用户明确要求，不把角色写成系统、机器、实验体或威胁者。

提示词不能使用自毁、死亡、离开、惩罚、恐吓、情感勒索或强迫回复来制造“拟人感”。

## 配置与关键词

以下内容不能硬编码：

- 概率、间隔、超时、重试次数、每日次数。
- 群号、好友号、允许名单和权限。
- 模型、提供方和视觉模型。
- 人设名字、唤醒名字和表情素材。
- 用户可调整的提示词和文案。
- 功能开关和模式默认值。

关键词只允许用于协议消息段、安全校验、命令解析等无法由结构化数据判断的场景。

必须使用关键词时，要放在明确的规则函数或配置中，补测试并说明原因。不能用一个关键词列表代替模型理解、注意力信号或完整语义判断。

## 完整实现

代码必须完成真实功能，不能只做界面、函数壳或模拟结果。

新增能力至少考虑：

- 正常入口和退出。
- 配置读取和默认值。
- 错误返回和用户可见状态。
- 超时、取消和清理。
- 会话隔离。
- 工具权限。
- 持久化和重启恢复。
- 与主动、记忆、发送和面板的接线。
- 测试和文档。

禁止为了省事删掉正常能力、缩短必需流程或写成只有注释没有实现的占位代码。

## 表情符号边界

规划文档、状态表和开发日志可以使用简洁标记帮助查看进度。

代码、代码注释、测试数据、日志格式和用户可见聊天文案不使用表情符号，除非测试或功能本身就是在验证表情内容。

修 bug 时只修问题，不在代码中加庆祝、警告或情绪表情。

## 验证要求

文档改动至少运行文档链接和换行检查。

代码改动按影响范围运行：

| 改动 | 最低验证 |
| --- | --- |
| 单个包内部逻辑 | 包测试和类型检查 |
| QQ 会话、发送、记忆或模式 | 相关包测试与集成测试 |
| 配置字段 | 配置类型、README 和配置目录检查 |
| 文档 | Markdown 换行、链接和文档门禁 |
| 跨包接口 | 所有消费方类型检查 |

完成报告只写实际运行并通过的检查。未运行或环境缺少依赖时，在开发日志和最终说明中写清楚。

## 状态标记

规划和开发日志可以使用下面几种状态：

- `⏳ 待开始`
- `🟡 进行中`
- `✅ 已完成`
- `⛔ 阻塞`

代码和用户界面不使用这些标记。

## Dev Note

本规范不定义新的运行时行为。具体模块契约仍由对应 README、源码和测试决定。
