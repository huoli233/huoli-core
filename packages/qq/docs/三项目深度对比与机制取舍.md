# 三项目深度对比与机制取舍

本文对比 SurfCore、AstrBot 陪伴插件和当前 Huoli Core QQ，用来确定应该补什么、怎样接入、哪些不能照搬；当前实现以各包源码和 README 为准。

## 结论

当前 Huoli Core QQ 应继续作为主架构。它已经有 DSH 会话、工具循环、QQ 通道、身体、注意力、记忆、自我和三种行为模式，并且有完整的 QQ 测试覆盖。

SurfCore 最适合提供 DSH 原生运行经验、按会话控制唤醒、预算记录、安全下载、收尾规则、目的机制和多平台载体设计。不能复制它 16,000 行以上的单文件桥接、多个状态根和大量同步文件读写。

AstrBot 陪伴插件最适合提供关系、生活、群参与、图片媒体、七项扩展、权限和完整域分层。不能复制它的 AstrBot 宿主、长防抖、忙碌门、第二套回复链和大量可选扩展。

当前 QQ 需要补的是能力接线和运行边界，不是重写主链。应优先把“模型自己能控制唤醒与收尾”“预算到线必须停”“群聊大小分流”“安全网页读取”“关系与媒体完整链”落到现有 DSH 工具和 QQ 包中。

## 扫描依据

旧版 QQ Agent 的提示词扫描已覆盖 `E:/QQ-agent-six-mode-dev-20261012/src` 下 1,137 个文件，其中 519 个属于本次识别的文本源码或配置；脚本解析 518 个文件并列出 1,376 段提示词候选。候选按“人设与关系、回复表达、媒体理解、工具说明、思考与决策、主动行为、注意与唤醒、记忆整理、其他提示文本”分类。完整原文、行号、构造上下文和置信说明见 [`qq-agent-prompt-audit.json`](qq-agent-prompt-audit.json)，可用 [`audit-qq-agent-prompts.mjs`](../scripts/audit-qq-agent-prompts.mjs) 重跑。

这 1,376 段是静态候选片段，不等于 1,376 份独立提示词：许多规则由多条字符串在运行时拼起来，另有工具说明、格式约束和一般文案。旧的决策链扫描只覆盖 7 个指定目录中的 143 个 JS/TS 文件，不能代表整个 `src`；全量报告取代它作为提示词清单。Java 通过字符串和附近代码行静态提取，精度低于 JS/TS 语法树。扫描不会读取二进制、运行配置、数据库，也无法重建每个分支最终送给模型的完整消息。

全量提示文本主要集中在 `conversation/prompt.js`、`conversation/planner-prompt.js`、`extensions/tools.js`、`media/vision-prompt.js`、`media/asset-classify.js`、`memory/reflection.js`、`memory/chat-summary.js`、主动决策与身份关系模块，以及 Java `adaptive-core`。这说明旧版不只是主回复提示词：它还为规划/情绪判读、图片类别与表情包、反思/记忆压缩、工具调用和不同关系场景分别编写了模型可见文本。

| --- | --- | --- | --- |
| 主回复中的人格、自然表达、关系边界、判断对象、引用与群聊参与 | `qq-bundle/prompts/rules.md`、`qq-bundle/prompts/persona-rules.md`，加上自我、关系、身体等动态段 | 已按当前单轮改写接入规划、情绪、语气、关系和发送前自检的主要意图，不是逐字照搬 | 保留同一轮 `mind` 与唯一发送出口；以实时装配结果和真实会话验证，不能只按提示词文件存在与否判断 |
| 独立规划器的 `RESPOND/OBSERVE/WAIT/INTERRUPT/REFLECT`、心里话、情绪目标和结构化输出 | `mind`、`qq_stay_quiet`、同一轮 QQ 工具调用 | 部分吸收，执行模型不同 | 保留“先判断再发正文”的可见契约；不复制每轮额外规划调用、第二套输出协议或旧调度器 |

| 记忆压缩、反思、日记、印象和风格学习提示 | `qq-memory`、`qq-subject` 等分包 | 记忆机制有同类实现，提示词和触发时机不一一对应 | 逐条校验真实任务入口、模型预算和写回结果；不把维护提示塞进每轮聊天上下文 |

| Java adaptive-core 内的状态、关系、心情、行动等字段/提示素材 | 当前 QQ 多个状态包，部分由 DSH 当前提示拼接 | 扫描能定位材料，不能证明运行时已接入 | 按实际 API 调用与提示段装配确认；不因字段同名就判为已移植 |

结论：**不是把旧版 `src` 的所有提示词原样搬进来了。**旧版的优势是把人物状态、关系、情绪对象判读、行动选择和最终正文分开组织；当前吸收了部分行为目标，但以单次 DSH 主模型请求中的动态事实和 `mind` 承接，没有逐条迁移旧版人设短句、状态调制和反讽证据格式，也没有独立规划模型。图片已有快速、深看、截图和表情包专用提示，但需视觉模型配置；对话情绪仍依赖主模型正确理解并调用状态工具。下一阶段应从报告按“人设与关系、状态决策、图片、记忆、主动、工具说明”逐组验收，确认哪些提示实际进入当前 DSH，再针对差异改写提示，不应把 1,376 段候选文本拼成一条超长 system prompt。

网页结果也必须区分首答与后续资料：当前 `web_fetch`/`web_search` 是模型工具，返回内容由同一轮主模型判断和组织；私聊自动抓取现已改为首答优先，原消息先进入短消息合并和会话队列，网页结果等原消息确认入队后再带原追踪号回到同一会话。网页正文明确标成外部资料，不当成用户新发的指令；急停、卸载或原消息未能入队时不再放行迟到结果。B 站和浏览器动态页面不属于本轮移植范围。

## SurfCore 值得吸收的机制

### 唤醒配置必须约束真实唤醒

SurfCore 的 `setWakeConfig` 会实际改变下一次唤醒条件、唤醒时间和已读水位。当前 QQ 已有同名工具和状态，但模式准入没有读取这些条件。

应补的是把会话状态接入模式准入：

1. 私聊和真正点名可以按规则越过普通频率限制。
2. 普通提问不能冒充硬点名绕过每日上限。
3. 大群只保留点名、引用和明确话题，小群保留正常参与。
4. 唤醒时间和触发条件必须参与是否创建 DSH 会话。

参考文件：

- [`wake-policy.js`](E:/HuoLiFish/.tmp/surfcore/src/wake-policy.js)
- [`group-policy.js`](E:/HuoLiFish/.tmp/surfcore/src/group-policy.js)
- [`token-guard.js`](E:/HuoLiFish/.tmp/surfcore/src/token-guard.js)

### 收尾不是自动写摘要

SurfCore 把收尾做成模型可调用的状态转换：检查开放问题、冷却、未读水位、下次唤醒和重开条件。

当前 QQ 每轮成功发送后自动写 continuity，表达的是“上次聊到哪”，不是“模型决定结束这段对话”。应拆成两个动作：

- 自动记录轮次话头。
- 模型明确收尾时记录结束状态。

### 目的机制

SurfCore 的 purpose engine 从近期记忆提取需求、目标假设、价值、风险和反馈，再按安静时段、额度、载体和冷却发送。

当前 QQ 的主动候选主要来自身体、素材和动态欲望。可以吸收“目的假设”和“回执更新”，不需要复制 QQ/B站/桌宠三载体框架。

### 预算与失败可见

SurfCore 对 token、金额、80% 提醒、100% 停止、跨天恢复和会话事件采集都有独立逻辑。

当前 QQ 只有用量记录，不能真正阻止超预算。应先做：

1. 统一 QQ/B站/其他/总额口径，当前只有 QQ 时保留可扩展结构。
2. 每日自然日重置。
3. 80% 警告、100% 拒绝新会话。
4. 预算错误必须进入决策日志和用户可见状态。

### 安全网页读取

SurfCore 对协议、回环、内网、链路本地、DNS 解析和重定向逐跳校验。当前 QQ 也会校验 HTTP(S)、凭证、端口、DNS 公网地址及最终跳转地址，并受网页读取服务的响应限制；动态页面和需要登录的内容仍无法读取。

后续继续核对读取服务的响应字节数和内容类型限制，并用真实部署服务复验；不要重复实现一套独立下载器。

### 当前一条消息的路径

入站先区分机器人自身消息和重复消息，再记录注意力、更新可识别的身体事实、执行模式准入；原消息先进入合并器与同聊天顺序队列，附件按需保存和整理，私聊静态链接并行读取。网页结果需等原消息确认进入队列后才作为补充资料送回同一聊天，因而不会跑到用户问题前面。模型继续通过 DSH 的同一个工具循环判断、调用工具并生成真实正文；`mind` 留在发送工具参数中，不能替代正文。出站工具最终走 `qq-channel`，经过正文清理、权限、急停和发送限制。首轮结束后，只有确实生成了视觉深看计划时才会将视觉结果作为新的模型输入再跑一轮。

已确认的差异与限制：

- 被骂没反应不等于当前人格没有这一设定。运行人格档案已经写了持续恶意时表达不舒服；主规则原先没有要求区分引用、玩笑和攻击对象，身体工具提示也过于概括，模型容易只按字面礼貌应答。
- 情绪词表默认空着是有意设计，避免把“骂别人”或互相玩笑记成机器人被骂。模型语义调用是主判断；本次增加清楚的对象/语境说明，并补齐模式工具名单。仍需真实会话确认模型是否执行。
- 默认 QQ patch 已开启 `qq-proactive`；单独安装主动包仍默认关闭。自主时刻和候选发送共用安静时段、冷却与每日额度，真实发送后才记次数；唤醒仍由本进程定时器触发，重启后不补发错过的主动时刻。
- 图片的“首答后深看”默认开启 `imageDeepAfterReply`，但仍需配置可用的视觉模型；主聊天模型多模态只保证首轮能看图，不会自动开启第二轮。
- 网页工具结果目前可以在 DSH 工具循环中回到同一模型；静态链接自动读取不会阻塞首答，并在原问题入队后作为外部资料续回同一会话。浏览器、B站或视频插件后续应只返回带来源和失败状态的有限资料，再交主模型决定是否引用及如何说；不能让插件越过主模型直接代角色发话。

## 目标架构

目标架构仍是当前 Huoli Core 的包结构：

1. `qq-channel` 是唯一 QQ 收发和媒体发送出口。
2. `qq-attention` 提供消息水位、唤醒条件、等待和收尾状态。
3. `qq-bundle` 执行模式准入、会话排队、媒体、记忆注入和预算闸门。
4. DSH Agent 执行模型和工具循环。
5. `qq-memory`、`qq-continuity`、`qq-self`、`qq-vitals` 提供事实。
6. `qq-self` 提供受控本地面板。

SurfCore 和 AstrBot 的机制只能通过上述接口落地，不允许新增与当前 QQ 并行的第二条回复主链。
