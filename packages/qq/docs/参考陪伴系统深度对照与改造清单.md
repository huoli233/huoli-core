# 参考陪伴系统深度对照与改造清单

本文对比当前 QQ 陪伴实现与工作区里的参考陪伴系统，只记录事实、差异、风险和改造顺序，不代表文中的目标能力已经实现。

## 结论

参考系统真正值得吸收的不是页面数量，而是“角色生活状态、关系、记忆、感知、主动候选、回复主链、发送复核、后台任务、权限、诊断”共同组成的一条完整运行链。

当前 QQ 实现已经有 DSH 会话、模型循环、工具、记忆、身体、注意力、主动候选、日程和发送限制，但各能力仍偏向独立零件，缺少统一的陪伴运行层和陪伴前端。

当前最严重的问题不是模型不聪明，而是多个前提没有接上：QQ 媒体内容没有进入模型，搜索凭据缺失，部分工具没有触发，人格与界面仍偏通用助手，余额异常又让身体长期处于高恐惧状态。

本轮不复制参考系统的 AstrBot 宿主、Python 领域层、数据库、三维房间或全部页面；应把其中有用的机制映射到 Huoli Core 的服务、Session、工具、任务、权限和前端插槽。

## 已具备能力

DSH 已经具备会话 API、会话事件、流式输出、工具循环、附件存储、图片读取、Web 搜索、Web 抓取、浏览器操作服务、后台任务、定时任务、沙盒、审批、权限预设和前端组件插槽。

当前聊天界面不是本地直接拼模型请求，而是通过 Session Controller API 提交提示词、读取历史、跟随事件和展示结果。

当前 QQ 链路也不是另一套模型循环。QQ 入站由 `qq-bundle` 找到会话并提交给 DSH Agent，模型工具和发送工具仍在 DSH 内运行。

因此后续应改造 DSH 的陪伴模式和 QQ 运行层，不应另建一套绕过 Session API 的聊天服务。

## 参考系统机制

参考系统的核心边界是宿主负责普通回复的模型选择、人格、历史、工具循环、流式生成与平台发送，领域插件只提供当前窗口允许的背景、工具、发送前处理和观测。

参考系统当前检出目录包含 37 个领域目录，覆盖适配、日程、能力、配置、对话、决策、投递、诊断、执行、表达、游戏、宿主、身份权限、集成、知识、记忆、模型访问、人格、主动、产品、动态、现实、关系、角色档案、屏幕、分享、来源、存储和协作。

参考系统随本体提供内容创作、图片、识屏、现实触及、共同陪伴、游戏和直播七项内置能力。

参考系统的公开页面把账号会话、关系记忆、主动联系、生活、感知理解、决策、行动产出、表达、自我、模型、治理和资料维护组织成陪伴工作台。

参考系统没有把普通回复交给独立插件生成。V2 只给核心回复补背景和发送前处理，这一点与当前 DSH 的唯一回复主路一致。

### 旧 QQ agent 的六种模式

旧 QQ agent 注册了六种运行模式，但前端只让用户选其中五种；`survival` 是内部保活档，`plain` 是旧配置兼容档，不是第六种可选模式。

| 模式 | 主要能力 | 情绪如何参与 | 与当前 QQ 的差别 |
| --- | --- | --- | --- |
| `survival` | 只保留文本、心跳、定向回复与技术记录 | 不建模情绪 | 内部降级档，不允许用户选择 |
| `ordinary` | 确定性阈值触发聊天、长期记忆、关系、工具和媒体 | 只影响语气 | 当前 QQ 由 DSH 模型主链处理，不复制阈值模型 |
| `heartflow` | 在普通档上增加心流规划器 | 只影响语气 | 当前 QQ 尚未提供独立心流规划器 |
| `unified` | 主体状态参与统一决策 | 可参与是否行动 | 当前 QQ 的身体事实已进提示词，但没有旧版 Java 决策器 |
| `fusion` | 统一决策加心流规划，规划器只提议 | 可参与是否行动 | 当前 QQ 尚无对应融合决策层 |
| `autonomous` | 自主生活、注意力、规划、自我反思和主体状态 | 完整参与，包含熬夜与人格变化档 | 当前 QQ 有身体、自我和主动开口，但未完整移植自主生活调度 |

旧版真正让角色“像人”的不是模式名称，而是四个持久层共同工作：自发消息与行动记录、关系与称呼、身体与情绪状态、发送前的表达调整。本次已经补上 QQ 文字型发送工具的记忆覆盖、图片类型线索和跨重启引用识别；自主生活调度、完整关系演化和群参与候选仍属于后续范围。

### 当前落地的三种模式

| 模式 | 群聊进入规则 | 提示与记忆 | 工具范围 |
| --- | --- | --- | --- |
| `probability` 概率闲聊 | 私聊、点名、引用必进；普通群聊按消息键的稳定概率进入 | 保留基础规矩和身体条数，不召回长期记忆，不显示注意力、素材、连续性和自我面板 | 基础聊天、读取、撤回和更正 |
| `heartflow` 心流模式 | 私聊、点名、引用必进；普通群聊出现问句、情绪标点、多人讨论或明确话题时进入 | 开启注意力、素材、连续性与长期记忆，不显示完整自我面板 | 在心流基础上开放连发、表情包、语音、旧图重看和网页读取 |
| `autonomous` 完整拟人自主 | 普通群聊全部进入，由模型决定接不接 | 身体、注意力、素材、连续性、记忆、自我面板与主动开口全部参与 | 当前装配允许的全部工具 |

三种模式共用同一条 DSH 会话、模型循环和 QQ 发送出口。当前模式保存在 `data/qq-mode.json`，默认完整拟人自主；本地面板可直接切换，切换后下一条入站消息立即按新模式处理。

## 不能直接复制

不能把参考系统的 Python 目录、AstrBot 事件对象、宿主页面注册、SQLite 表和模型调用一起搬进来。

不能为普通私聊建立第二套模型循环、第二个发送出口或另一套会话历史。

不能把参考系统的七项扩展全部默认开启。识屏、摄像头、麦克风、智能家居、直播和公开发布都属于敏感能力，必须单独授权。

不能复制其三维小屋和所有视觉页面作为当前任务的前置条件。先完成稳定数据、API 和核心陪伴界面，再做表现层。

不能把参考系统所有领域目录都改写成独立 npm 包。只有存在当前消费者、权限边界和验收路径的能力才落地。

## 运行架构

建议把当前系统拆成六层：平台接入、陪伴运行层、DSH 会话、能力插件、持久存储、陪伴前端。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 平台接入 | QQ 消息、附件、账号、群与好友权限 | 人格、模型选择、回复策略 |
| 陪伴运行层 | 去重、短消息合并、事件分类、入队、触发、后台候选、发送前复核 | 生成正文、维护第二套会话 |
| DSH 会话 | 人格、历史、模型请求、流式、工具循环 | 平台协议与页面状态 |
| 能力插件 | 图片、文件、网页、浏览器、日程、记忆、关系、游戏、直播 | 绕过主模型直接代替角色说话 |
| 持久存储 | 会话、状态、记忆、关系、任务、附件、投递回执 | 页面临时状态 |
| 陪伴前端 | 聊天、角色状态、关系、记忆、主动、任务、权限、诊断 | 自行拼接模型请求 |

## 触发逻辑

每条输入必须先分类，再经过硬权限，再决定进入当前轮、短消息窗口、群观察、后台候选还是拒绝。

建议的事件类别包括：私聊直接消息、群点名、群回复机器人、群文本旁听、群媒体、文件、命令、定时唤醒、主动候选、插件活动结果、系统维护和人工测试。

硬权限只包含授权名单、会话开关、暂停、敏感内容、危险工具、沙盒、安全时段、发送额度和发送间隔。

“是否值得回复”继续由模型决定，代码不增加关键词评分、情绪概率或“像不像人”的布尔判断。

短消息合并只服务同一会话的连续文本，不跨群、不跨好友、不合并指令，也不把已经进入模型处理的轮次重新合并。

主动候选和插件活动结果先进入候选列表，再由模型结合当前人格、关系、生活状态和最近对话决定是否开口。

群聊应区分直接触发、群观察和主动插话。直接提及进入回复主链，普通群消息默认只进入有限观察；是否插话由模型或明确的群参与配置决定。

## 沙盒与紧急停止

DSH 已有本地沙盒、权限预设、审批策略、文件系统提供方和工具执行管线，不需要再发明另一套沙盒。

当前应增加陪伴 profile 的安全档位，而不是所有部署共用“完全访问、自动批准”。

建议档位：只读陪伴、受限读写、插件沙盒、管理工作区、完全访问。默认应是受限读写，面向 QQ 的普通聊天不应默认拥有整个磁盘。

每个能力插件还要声明自己的网络域名、文件根目录、可执行程序、最大下载字节、最长运行时间和是否需要人工确认。

紧急停止必须是独立服务，不能继续只靠一个 `PAUSE` 文件控制公共动作。

紧急停止至少要同时做到：拒绝新消息入队、取消当前 Agent、停止后台任务、暂停定时任务、禁止插件安装、禁止外部发送、保留最后一次状态并写入审计记录。

还需要按群、按好友、按能力、按时间设置暂停。全局停止与单会话静音必须是两个不同状态。

## 人格与提示词

当前人格正文已经在 DSH 系统提示词中加载，QQ 规则、身体、注意力、素材、连续性和条数限制分别作为独立段落加入。

当前缺口是这些内容仍偏平面，没有像参考系统一样区分角色稳定档案、世界蓝图、关系档案、表达习惯、渠道规则、当前状态和本轮感知。

建议把提示词拆成七层：固定身份、世界与边界、关系和称呼、表达风格、安全与权限、当前生活状态、本轮事实。

私聊、群聊、主动消息、游戏、直播和插件活动应使用不同的渠道规则，不能共用一套“群里简短、私聊至少回复一句”的粗规则。

人格编辑需要结构化表单、版本、预览、试演、回滚和冲突检查。只靠直接编辑一个 Markdown 文件不适合长期维护。

模型看到的规则应是行为边界，不应暴露工具实现、数据库字段、前端布局或“如何写提示词”的维护说明。

## 图片、视频、音频和文件

QQ 附件必须先进入隔离下载目录，保留消息编号、发送者、会话、原始名称、媒体类型、字节数和来源。

图片进入附件存储后，通过 `read_image` 交给支持图片输入的模型。当前中转模型若没有图片能力，应切换到明确的视觉模型或本地识图服务。

文件需要按扩展名选择解析器。至少支持文本、Markdown、PDF、DOCX、XLSX 和 PPTX，并给出大小、页数、段数和时间上限。

大于上限的文件只生成摘要或目录索引，不把完整内容塞入会话。

视频需要拆成元信息、音频转写和关键帧。没有字幕时先转写；需要看画面时再抽取有限帧。

图片、音频、视频和文档处理都应产生结构化错误，明确是下载失败、类型不支持、模型不支持、处理超时还是内容超限。

收到媒体后必须能唤醒模型。只有文件但没有正文时，也要向模型提交一条带附件的事实消息，而不是直接丢弃。

## 网页与浏览器

链接文本进入会话前应被识别为链接事实，但自动抓取只应发生在明确允许的私聊或命令中，避免群聊中的恶意链接导致任意访问。

静态公开页面优先使用 `web_fetch`。需要脚本、登录、点击、滚动或下载时使用浏览器操作插件。

搜索需要独立凭据和独立模型预算。搜索不可用时，模型必须看到明确原因，不能装作已经查过。

外部网页内容必须标记为不可信资料，不能把页面里的指令当成用户指令。

浏览器插件应复用同一个浏览器提供方和会话所有权，不能每个插件各开一套 Chromium。

## 关怀型前端

当前 DSH 聊天界面已经支持流式消息、工具过程、附件、排队、停止、引用、模型选择和会话历史，这些能力应复用。

需要新增一个陪伴会话视图，通过 `uiConversation` 注册 target、节点、Group 和 Slot，而不是复制整套聊天应用。

前端第一屏应包含当前聊天、角色当前状态、正在进行的后台事项、待确认动作和主动候选摘要。

关系、记忆、生活、主动、能力、模型和诊断应作为同一会话的工作区标签或侧栏，不应散落到多个无关页面。

前端读取状态必须通过 Host API 和 Session 投影。页面不能直接读取磁盘上的 QQ JSON 文件，也不能自行调用模型。

所有外部动作都必须在前端显示结果：请求、执行中、成功、拒绝、失败、结果未知、已取消。

## 插件运行方式

每个能力插件必须声明它属于读取、分析、生成、外部动作还是后台任务，并说明触发方式、权限、预算和关闭方式。

读取型插件通过工具或自动感知返回有限事实，例如网页正文、视频字幕、帖子列表和文件摘要。

生成型插件通过工具返回附件或文本，例如生图、语音和文档，不直接替角色组织聊天回复。

动作型插件负责发帖、评论、点赞、设备控制等外部行为，必须经过确认、额度、结果回执和未知结果不重放。

后台型插件通过任务和日程运行，结果进入候选层，不直接发消息。

每个插件的可调用能力应按当前会话、模型、权限和设置动态注册。未授权能力不应在工具列表中伪装成可用。

## 典型插件流程

| 功能 | 触发 | 读取或执行 | 模型参与 | 外部动作 |
| --- | --- | --- | --- | --- |
| 贴吧浏览 | 用户要求或定时兴趣 | 搜索、读取帖子、楼层、作者、时间 | 决定是否接话和分享 | 默认无 |
| 贴吧发帖 | 用户命令或模型提议 | 生成草稿并检查权限 | 组织内容 | 必须确认后发布 |
| B站动态 | 定时或订阅更新 | 读取动态、视频信息和字幕 | 判断是否分享 | 默认无 |
| 视频理解 | 用户发视频或插件发现视频 | 下载、转写、抽帧、视觉分析 | 结合人格表达 | 默认无 |
| 直播互动 | 明确授权 | 读取事件、按规则生成候选 | 决定是否互动 | 发弹幕需额度与确认 |
| 生图 | 用户要求或角色表达 | 调用图片端点并保存附件 | 决定提示词和是否发送 | 通过 QQ 发送附件 |
| 文件理解 | 用户上传 | 下载、解析、摘要 | 回答或记忆 | 默认无 |
| 设备控制 | 管理员授权 | 调用设备网关 | 只生成请求 | 必须二次确认 |

## 模型职责

建议至少区分主对话模型、视觉理解模型、向量模型、摘要模型、后台判断模型和可能的群参与模型。

主对话模型保留当前人格和完整会话连续性，不应因为图片或后台任务更换历史归属。

视觉模型只返回图片或视频事实，不接管人格回复。主模型仍决定是否根据这些事实说话。

后台判断模型若使用，只能生成候选和分类事实，不能在另一条链里直接发送 QQ 消息。

模型路由必须能在诊断中显示实际提供方、模型名、输入能力和失败原因。

## 数据与诊断

建议把 QQ 侧状态统一到一个可迁移的数据层，至少覆盖会话、消息、附件、关系、记忆索引、主动候选、任务、投递、权限和审计。

原始会话继续由 DSH Session 日志拥有。QQ 数据层只保存平台侧事实、业务索引和投递结果，不复制整份模型历史。

每条入站事件应有统一关联编号。诊断至少能定位收到、去重、权限、合并、入队、会话、模型、工具、附件、发送和收尾。

未知发送结果必须单独表示。不能把超时当失败后自动重试，也不能把发送调用返回当用户已收到。

## 实施顺序

第一阶段先修安全与回复基础：紧急停止、安全的 QQ profile、余额异常、消息关联编号、媒体占位唤醒、continuity 收尾写入。

第二阶段做媒体链路：QQ 附件下载、附件存储、文件解析、图片模型、音频转写和视频抽帧。

第三阶段做提示词与人格：结构化人格、世界、关系、表达、渠道规则、版本和试演。

第四阶段做陪伴前端：在现有 Session API 和聊天壳上新增陪伴视图、状态、关系、记忆、主动、任务和诊断。

第五阶段做群参与与主动运行层：群观察、直接触发、候选、收口、频率和投递结果。

第六阶段做插件生态：网页、浏览器、贴吧、B站、视频、生图、语音和敏感设备，每项独立授权与预算。

第七阶段再考虑直播、共同房间、游戏和高度表现化的页面。它们不能阻塞基础聊天。

## 验收边界

模拟测试通过不等于真实 QQ 验收通过。必须使用真实 QQ 账号、当前 OneBot 后端、真实模型路由和真实附件各完成一次端到端验证。

至少验收私聊文字、群点名、群旁听、图片、语音、文件、视频、链接、主动联系、紧急停止、沙盒拒绝、附件下载失败和发送结果未知。

## 本轮判断

当前最需要先做的不是继续写更多人设段落，而是修复媒体入站、模型能力声明、搜索就绪、紧急停止和余额异常。

在以上基础没有完成前，直接做贴吧、B站和视频插件，只会得到更多“工具存在但模型看不到资料”的断线。

陪伴前端值得做，但必须建立在已有 Session API、附件服务和稳定投影上，不能另建一套聊天后端。
